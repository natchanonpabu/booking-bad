# ADR-001 — Backend stack for Winner Court

**Status:** Accepted
**Date:** 2026-09-08
**Deciders:** Founder (F) + Engineering (E). Consulted: the four architecture proposals and their three independent reviews (2026-09-08).
**Supersedes:** the one-sentence stack sketch in `00-roadmap.md` §5 ("Fastify on Cloud Run with `min-instances=1` over Lambda (it must hold MQTT and server-side timers)") and `prd.md` §6.2 (Prisma, Redis, Mosquitto, WebSockets).
**Scope:** Plan 03 (Foundations) and everything it constrains. This ADR does not decide the payment provider, the slip-verification vendor, or whether IoT ships — see §5.

---

## 1. Decision, in one sentence

**One always-on Fastify 5 process on Node 24 in Singapore, serving the LIFF SPA and the API from a single origin, over one managed PostgreSQL 17 with an `EXCLUDE USING gist` constraint as the only thing that prevents a double-booked court — with `pg-boss` for timers, Cloudflare R2 for slips, and no Redis, no message broker, no second runtime, and no orchestrator.**

Everything else in this document is either the reason for that sentence, or a named consequence of it.

---

## 2. Context

### 2.1 Why now

Plan 01 (frontend booking demo) was approved on 2026-09-15 and is built at `booking/apps/liff/`, in the same repository as `documents/`. Its `src/data/types.ts` is declared "the API contract Plan 02 implements," and it is promised to merge into the backend **unedited**. Plan 03 begins with `git init` and `migrations/0001_core.sql`. Both of those commits are difficult to reverse: the first fixes the repository shape, the second fixes the schema that the exclusion constraint, `availability()` and the money type all live in. Deciding the stack after those commits means deciding it by accident.

There is a second reason for the timing. Plan 01 as first drafted rendered `฿{total}` from a `Baht = number` (merged to `Satang` in Plan 01 Revision 4, 2026-09-15). The backend requirement is `bigint` satang everywhere. Those two sentences cannot both be true, and every day Plan 01 runs unamended makes the correction more expensive. §4.4 amends Plan 01 today.

### 2.2 What constrains the choice

| Constraint | What it rules out |
|---|---|
| **LINE platform.** LIFF ID tokens verified server-side; Messaging API push/reply; inbound webhooks signed HMAC-SHA256 over the **raw** body; Flex Message JSON. | A framework where the raw body survives only by middleware-ordering discipline. An edge/serverless runtime that cannot hold a warm pool or a persistent listener. |
| **Thai payments.** PromptPay through a licensed acquirer, webhook confirmation, idempotency, and — the failure that actually costs a customer their court — a webhook that **never arrives**. | Treating the webhook as the source of truth. A platform-level merchant account (that is money transmission — D25/D73). |
| **Tiny pilot scale.** One venue, six courts, ~30 bookings/week ≈ 130/month, ~฿57,200 GMV. Peak is Friday 19:00–21:00. | Anything justified by throughput. Caches. Shards. Read replicas. A queue vendor. |
| **1–3 people, Bangkok, hiring locally.** | Any component whose failure mode requires a specialist. Kubernetes. A self-hosted broker. A self-hosted log stack. Four identity mechanisms for ten users. |
| **No written budget or deadline (D71).** Cost is a real constraint, not a rounding error. | Anything whose idle cost exceeds its value at one venue. The idle cost is stated explicitly in §6. |
| **Plan 01's `types.ts` is the contract.** | Codegen pipelines that discard the contract's shape and regenerate it from something else (OpenAPI→TS, ORM→client, server→tRPC inference). |
| **Multi-tenancy from migration 1 (D66).** `venue_id` on every table even though the owner UI is four screens. | Retrofitting tenancy. A per-venue schema or database. |
| **Asia/Bangkok, Buddhist-era display.** Booking inventory is keyed to a **venue business day**, not a UTC instant (§3.2 — the business-day rule, which deliberately differs from the calendar day for a venue closing after midnight). | Any model where the inventory key is a `timestamptz` and every query converts. |

### 2.3 The three failures this backend exists to prevent

Stated up front because every layer below is scored against them:

1. **A court sold twice on a Friday at 19:00.** Three code paths insert bookings — the LIFF client, duel-accept, and the counter walk-in. Application guards will not survive all three.
2. **A payment webhook that never arrives**, leaving a customer who paid ฿440 standing at a court the system shows as free. This failure is silent: no exception, no log line, a green uptime check.
3. **A raw request body destroyed by a JSON parser**, so LINE's HMAC never verifies — the named #1 day-one bug on every LINE integration.

Failure 1 is solved by a Postgres constraint. Failure 2 is solved by inverting the confirmation path. Failure 3 is solved by framework encapsulation. None of the three is solved by a framework benchmark, a cache, or a queue.

## 3. The decision, layer by layer

### 3.0 Version policy — read this before the tables

Every version number circulated in the four source proposals disagreed with at least one other proposal, and none can be verified from inside this repository. **Treat the "Version" column below as a major line, not a pin.** On day 1 of Plan 03, run `npm view <pkg> version` for each dependency, write the exact resolved versions into §10.1 of this file as an amendment, and commit `pnpm-lock.yaml`. `tailwindcss` stays pinned exactly at `3.4.17` with no caret, per Plan 01 §4.3.

**One version below is already suspect and is named here so nobody pins it from this document: `@line/bot-sdk` 11.x.** The published line is 9.x/10.x; 11.x appears to have been invented somewhere in the source proposals and then copied forward. Every `@line/bot-sdk` cell in §3.4 means "whatever `npm view @line/bot-sdk version` returns on day 1" — resolve it into §10.1 before the first push is written, and do not let a fabricated major reach `package.json`.

### 3.3 The domain-critical layers

| Layer | Choice | Version | Why — for *this* project | Rejected, and why |
|---|---|---|---|---|
| **The exclusion constraint** | `EXCLUDE USING gist (venue_id WITH =, court_id WITH =, play_date WITH =, int4range(start_min, end_min, '[)') WITH &&) WHERE (occupies_slot)`, on a `booking` table keyed by `(court_id, play_date, …)` | migration `0001_core.sql` | The single most important line in the repository, and the entire concurrency story for all three insert paths. Postgres raises SQLSTATE **`23P01`**, which one error translator maps to HTTP 409 `SLOT_TAKEN`. **`play_date WITH =` is not optional and its omission is a product-killing bug, not a nit:** without it the constraint compares every booking on Court 3 at 19:00 against every *other day's* booking on Court 3 at 19:00, and **the second booking ever taken for that court-hour — on any future date — is rejected as `SLOT_TAKEN`.** The product is unusable on day 2, and the 20-concurrent test does not catch it because it exercises one court-hour on one date; §3.5's different-`play_date` regression test is the one that does. `btree_gist` is already installed, so `date WITH =` works. `now()` cannot appear in an exclusion-constraint predicate (index predicates must be `IMMUTABLE`), which is what forces the hold design below — and that turns out to be the better design anyway. **The predicate keys off `occupies_slot boolean NOT NULL`, not off `status`, and that is a deliberate operational decision** — see the row below. | **A materialised `court_slot` table** — rejected *in writing*, here, so it is not re-proposed in month two: 6 courts × 13 hours × 90 days is 7,020 rows of duplicated truth that drifts the moment a `rate_rule` row changes. **Application-level overlap checks or `SELECT … FOR UPDATE` on a court row** — will not survive all three insert paths. **The two-dimensional variant** (adding a hold-liveness range so expiry is self-enforcing) — genuinely elegant, genuinely correct, and the least hireable DDL anyone proposed. It is recorded as a **considered rejection** in `db/README.md` beside the design we chose, with the reason, so it is a decision rather than an idea someone re-invents in month six. |
| **Why the predicate is a boolean, not a status list** | `booking.occupies_slot boolean NOT NULL`, maintained in the same statement that writes `status`, plus a **separate** `CHECK (occupies_slot = (status IN ('held','confirmed','checked_in','completed')))` that ties the two together. | `0001_core.sql` | Postgres has **no `ADD CONSTRAINT … EXCLUDE USING INDEX` and no `NOT VALID` for `EXCLUDE`.** If `status` sits in the exclusion predicate, then the day someone adds `'no_show'` or `'refunded'` — a certainty, not a hypothesis — the only way to change the predicate is to **DROP and rebuild the GiST constraint under an `ACCESS EXCLUSIVE` lock**, which on a table under Friday-night writes is a maintenance window and an outage for the product's one guarantee. With a boolean in the predicate, the exclusion constraint **never changes again**: adding a status is `ALTER TABLE booking DROP CONSTRAINT booking_occupies_matches_status, ADD CONSTRAINT … NOT VALID` (CHECK **does** support `NOT VALID`, then `VALIDATE CONSTRAINT` under a `SHARE UPDATE EXCLUSIVE` lock) plus one line in the app. The price is honest and stated: `occupies_slot` is a second, app-maintained fact about a row, and the CHECK is what stops it drifting. ## 4. The three contested decisions

### 4.1 Does maybe-IoT justify an always-on process?

**No. Strike that justification from the record. Keep the always-on process for reasons that are certain.**

The roadmap's ADR sentence is: *"Fastify on Cloud Run with `min-instances=1` over Lambda (it must hold MQTT and server-side timers)."* Three things are wrong with it.

**First, the justification is load-bearing on a maybe that the project has already leaned against.** D37's own recommended answer is that IoT does **not** ship in v1. Roadmap §5 says a ฿1,500 clamp meter may cancel it permanently, and critique #10 says IoT is already over-invested against the register. Letting a feature the project expects to cut select the hosting platform is how an organisation with no written budget (D71) acquires a permanent monthly bill. A justification that would be **orphaned** by a decision the register recommends making is not a justification.

**Second, the technical claim does not survive inspection even in the world where IoT ships.** An MQTT subscription is a **singleton**; an API must be horizontally scalable. Those two properties are incompatible in one process. And `min-instances=1` is a **floor, not a ceiling** — under any concurrency spike the platform starts a second container, at which point you have two MQTT clients sharing a client-id kicking each other off the broker, and court lights that intermittently do not turn on. So `min-instances=1` never actually delivered the singleton semantics it was reaching for. When IoT ships, the MQTT client gets its own deployable or an advisory lock, on any platform — which means it was never an argument about the API's compute model at all.

**Third — and this is why the conclusion survives anyway — the always-on process is correct for reasons that are certain in v1:**

- the **T−30 LINE reminder** must fire for a booking made six hours earlier;
- the **payment reconciliation poller** is the primary confirmation path (§3.4) and must run whether or not anyone is holding a page open;
- the **nightly settlement pull** and the **slip retention purge** are scheduled work with no request to ride on;
- a warm connection pool matters on a screen where **first paint is the pitch**, on Thai mobile data, inside a webview.

Note carefully what is **not** on that list: **the hold** (15 minutes at pilot, §3.3). Hold correctness does not depend on any scheduler — the reap is transactional inside every insert path and `availability()` filters expired holds on every read (§3.3). That is deliberate: if the process is down for six hours, no inventory is lost and no booking is wrong. Requirement #4 asked for a hold that "releases inventory without a cron the team has to babysit," and the answer is ~6 lines of SQL, not a subsystem.

**Consequence for the ADR text.** The sentence in `00-roadmap.md` §5 is replaced by:

> *Fastify 5 on Node 24, one always-on process in Singapore, over one managed Postgres. Chosen because the T−30 reminder, the payment reconciliation poller and the nightly jobs all ship in v1 and all need a process that is awake — **not** because of IoT, which per D37 does not ship in v1, and whose MQTT client will get its own advisory-locked deployable when and if it does. No Redis and no message broker: `pg-boss` is a table in the database we already back up.*

**And the cost record is corrected while we are here**, because the original argument was made on a wrong number in both directions: a Cloud Run min-instance with CPU **throttled** (the default) bills roughly **$9/month**, not $50 — the $50 figure is `--no-cpu-throttling`. Price is therefore **not** why we are not on Cloud Run. The reasons are that throttled CPU means in-process timers do not reliably fire (a correctness problem, and the very thing the sketch wanted), that there is no pre-deploy migration hook, and that it brings seven Google products and an IAM model for a team of two.

### 4.2 ORM / query layer — Kysely, and what happens to the three hard things

**Decision: Kysely over `node-postgres`, with table types generated from the live database by `kysely-codegen` and `sql\`\`` template literals for anything it cannot express.**

The deciding property is **which direction the truth flows.** Every object this product's correctness depends on — the exclusion constraint, the `availability()` function, `int4range`, the money CHECKs — can only be written as SQL. So the database must be the source of truth and the TypeScript types must be **derived from it**. Kysely owns nothing and generates nothing: what you write is what runs.

**What happens to each of the three hard things:**

| Hard thing | Under Kysely |
|---|---|
| **`EXCLUDE USING gist`** | Lives in `db/migrations/0001_core.sql` as hand-written SQL, exactly as W7 specifies. Kysely neither knows nor cares about it — and crucially, **no tool in this stack will ever propose dropping it**, because nothing is diffing a TypeScript model against the database. The insert path is an ordinary `INSERT` whose failure mode is SQLSTATE `23P01`, caught by one translator. The **test suite** asserts `SELECT 1 FROM pg_constraint WHERE conname = 'booking_no_overlap'` after applying every migration to a fresh database — one owner, inside the tests; §3.5 deliberately keeps no separate CI job for it. |
| **`bigint` satang** | `pg.types.setTypeParser(20, v => { const n = Number(v); if (!Number.isSafeInteger(n)) throw …; return n; })` in `db/index.ts`, with the comment. Yes, Kysely's default is int8 → `string`; the correction is **one line** with a guard, in the same file as the `date` parser, and it is the same line every proposal that used `pg` needed. Codegen then types the column `number`, which the contract brands as `Satang`. |
| **Range types** | `int4range(start_min, end_min, '[)')` appears in the constraint and in the reap predicate as `sql\`\`` template literals. `kysely-codegen` types a range column as `string`; we do not select ranges into application code — the columns we read are `start_min` and `end_min` as plain integers, which is the whole reason §3.2 chose minutes-from-midnight over `tstzrange` as the inventory key. |

**Rejected, with the reasons that decided it:**

- **Prisma** (the PRD's pick, §6.2) — **reject by name, in this ADR.** It cannot express `EXCLUDE USING gist`, `btree_gist` or range types in `schema.prisma` at all, so the most important line in the codebase would sit outside the model Prisma believes it owns; its migration engine diffs against that model and will therefore propose removing what it cannot see. It maps `bigint` to JS `BigInt`, which `JSON.stringify` **throws** on — a guaranteed 500 on the first `GET /bookings`. Its view support is awkward. It ships a query-engine binary in the container. It is the most hireable option in the field and it is still rejected, because *a stack that hides the exact Postgres features your correctness depends on is not boring, it is just familiar.*
- **Drizzle** — the honourable runner-up, and better than Prisma here: `bigint({ mode: 'number' })` gets satang right by default, and `drizzle-kit generate` produces SQL files you can hand-edit. Rejected because it still wants the TypeScript schema to be the truth, it has **no exclusion-constraint builder and no range types**, and `drizzle-kit push` would happily propose dropping a constraint it cannot represent — so the design needs a CI grep banning its own tool. When the escape hatch is where 60% of the important DDL lives, the DSL is not earning its place.
- **Raw `pg` with hand-written row interfaces** — the interfaces drift silently, which is exactly the bug class this decision exists to prevent, and a hand-written `Database` interface is manual work a busy team will skip. Codegen + a CI diff is the version that stays true.
- **postgres.js (porsager)** — faster and nicer; fewer Bangkok hires know it, and tagged templates make logged SQL less greppable.

**Three honest costs, all accepted, none of them free:**

1. **The generated type file is a build artifact that can go stale.** A developer who edits a migration and forgets to regenerate gets a confusing local failure before CI catches it. Accepted, because the alternative is a schema whose truth lives in TypeScript.
2. **`kysely-codegen` needs a *live* database, so every contributor needs Docker just to typecheck.** This is not a CI detail — it is onboarding friction with a name: a designer who only wants to edit a Flex template or a Tailwind token has to install Docker, start `postgres:17` and run `dbmate up` before `tsc -b` will pass. Two mitigations, both cheap: the generated `db/types.ts` is **committed**, so a clean checkout typechecks with no database at all, and regeneration is only needed by someone who changed a migration (§3.5 keeps it a local step, not a CI gate); and `pnpm db:up` wraps the container, the migration and the codegen in one script so it is a single command rather than a page of README.
3. **The `expectTypeOf` contract tests do not run by default, and if that is missed the "both sides agree" guarantee is silently zero assertions.** `vitest` executes `*.test-d.ts` type assertions only under **`vitest --typecheck`** (or with the files explicitly in the tsconfig `include` that `tsc -b` walks). §3.5's CI list runs `tsc -b` and `vitest`, and neither of those, as ordinarily configured, evaluates a single `toEqualTypeOf`. So: **`typecheck: { enabled: true, include: ['**/*.test-d.ts'] }` in the Vitest config, and one deliberately-broken assertion committed once, run, and confirmed red before it is deleted.** A guarantee nobody has watched fail is a guarantee nobody has.

### 4.3 One repo or two, and how `types.ts` becomes the API contract

**Decision: one repository, one pnpm workspace, four packages — `apps/liff`, `apps/api`, `packages/shared`, `packages/tokens`. No Turborepo, no Nx, no `apps/owner`, no published contract package.**

Two repositories would force `@winnercourt/shared` to become a published npm package with a version number, which turns a contract change into publish → bump → install → PR instead of one commit. At 1–3 people sitting in the same room, that friction is not discipline — **it is the reason people stop updating the contract**, and the contract is the artifact this whole plan rests on. It also means the API and the frontend deploy from one artifact and one origin, which is what deletes CORS (§3.5).

`packages/shared` is consumed **as TypeScript source** — `"exports": { ".": "./src/index.ts" }`, no `dist`, no build step, no watch task — so editing the contract during Plan 04 is a save, not a pipeline. It compiles to ES2020 and imports only `zod`, which is what keeps it safe inside an old Android WebView. A lint rule bans `node:*` imports from it; one accidental `import { createHash } from 'node:crypto'` in a shared helper and the Vite build either fails or ships a polyfill into the webview.

**The mechanism, in full — there is no codegen anywhere in it:**

1. `packages/shared/src/contract/types.ts` **is Plan 01's file**, which already lives at `apps/liff/src/data/types.ts` in this same repository (Plan 01 decision 10) and moves with a plain `git mv` — history preserved, its 19 state-machine tests intact, no subtree import.
2. `packages/shared/src/contract/schemas.ts` sits beside it with the Zod validators the API registers per route.
3. `packages/shared/src/contract/contract.test-d.ts` asserts `expectTypeOf<z.infer<typeof BookingSchema>>().toEqualTypeOf<Booking>()` for every response type.
4. `tsc -b` at the repo root type-checks all four projects **in one pass against the same source** — **plus `vitest --typecheck`**, which is the half people forget: `tsc -b` compiles the app, but the `*.test-d.ts` assertions in step 3 are only *evaluated* under Vitest's typecheck mode or by explicit tsconfig inclusion (§4.2). Those two commands together are the "both sides agree" guarantee; either one alone is a guarantee running zero assertions.
5. `apps/liff/src/data/api.ts` — which Plan 01 deliberately built as an async facade with fake latency — swaps its body for `fetch()`. **No screen changes.** That seam exists because Plan 01 designed for it.

**Two owner-surface decisions that follow:** the four D65 owner screens are **guarded routes inside `apps/liff`**, not a second SPA — four screens do not justify a second design system that will drift. And `packages/tokens` is Plan 01's `tailwind.config.js` promoted to a preset plus `--wc-*` custom properties, exactly as roadmap §5 already specifies.

### 4.4 Amendment to Plan 01, required before any component is written

"`types.ts` merges unedited" is **~99% true, not literally true.** Three type edits — one afternoon — plus **a fourth amendment that is not a type change at all and is the larger of the two**, and they must land **before** Plan 01 builds the components that render money and the checkout screen that confirms a booking:

1. **`Baht` → branded `Satang`.** Replace `export type Baht = number` with:
   ```ts
   export type Satang = number & { readonly __satang: unique symbol };
   export const satang = (n: number): Satang => {
     if (!Number.isInteger(n)) throw new Error(`satang must be an integer: ${n}`);
     return n as Satang;
   };
   const THB = new Intl.NumberFormat('th-TH', { style: 'currency', currency: 'THB' });
   export const formatTHB = (s: Satang): string => THB.format(s / 100);   // ฿440.00
   ```
   **Display convention (decided in Plan 01, 2026-09-15):** customer-facing prices render without decimals when they are whole baht (`฿440`) and the PromptPay transfer amount always shows two (`440.00`). Plan 01's `lib/money.ts` implements that as `thb()` and `payAmount()` on top of the same `Intl.NumberFormat` rule below; `formatTHB` here is the two-decimal form and is what `payAmount` builds on. **This block is the single definition of `Satang` and `satang()` — §9.3 shows the same file, not a second version.** Two details that an earlier draft got wrong and that are worth the four extra lines: `satang()` **guards on `Number.isInteger`** (a brand cast that accepts `440.5` makes the whole `bigint` column a lie at its only construction site), and `formatTHB` uses **`Intl.NumberFormat`, not `toLocaleString`** — `` `฿${(s/100).toLocaleString('th-TH')}` `` renders ฿440.00 as **`฿440`** and ฿440.50 as **`฿440.5`**, which is a price tag no Thai customer reads as money and a receipt no venue accepts. Currency formatting is exactly the thing being fixed by this amendment; getting it wrong in the amendment itself is how the bug survives.

   **Merged into Plan 01 on 2026-09-15** (Revision 4), together with item 3. Item 4, the friendship gate, is deferred to Plan 04 because the frontend-only demo sends no LINE messages. Six fields change: `RateRule.pricePerHour`, `Slot.price`, `QuoteLine.unitPrice`, `QuoteLine.amount`, `Quote.total`, `Booking.total`. `data/rates.ts` fixtures get `× 100`. Every render site goes through `formatTHB` — `lib/format.ts`'s `thb()` becomes that function. The brand makes the unsafe construction a compile error, so ฿440 is `satang(44000)` in one place and cannot silently become 44,000 baht.
2. **`Booking.courtIds: CourtId[]` keeps its shape on the wire**, with a comment recording that the server stores N rows sharing a `booking_group_id` because the exclusion constraint is per court (§3.3).
3. **`Quote` gains `quoteToken: string`** and **`AvailabilityBlock` gains `venueId: string`** — the first so `POST /holds` can reject a client-computed total, the second because D66 puts `venue_id` on every table from migration 1 and the contract should say so from commit 1.
4. **The OA-friendship gate on checkout — and this one is bigger than the `Satang` change.** `Satang` is a find-and-replace behind a compile error: the type system finds every site and nobody has to design anything. This is a **screen**. Checkout gains a state for `oaFriend === false` (an add-friend step above the confirm button, in Thai, that does not block confirming), the confirmation screen becomes a **delivery mechanism rather than a courtesy** — booking reference, `.ics` download, venue phone number — and `contact_phone` becomes required at checkout rather than optional. The contract picks up `oaFriend: boolean` on the session/user shape and `icsUrl: string` on `Booking`. **The reason is §3.4's friendship row: `pushMessage` fails for a user who never added the OA, so without this the customer who prepaid ฿440 gets nothing at all.** Half a day of design and a day of build, not an afternoon — which is exactly why it is written here, before Plan 01's checkout is built and not after.

### 4.5 Why not Go — the runtime, contested properly

Four backend proposals were judged and **all four were Node**, so the runtime was assumed rather than decided. It is contested here so that month fourteen finds reasoning instead of an assumption.

**Go is entirely capable of this backend, and on four specific axes it is better than what §3.1 chose.** (1) **Money:** `type Satang int64` replaces a branded `number`, a runtime `Number.isInteger` guard at the constructor, `setTypeParser(20, …)` with a `Number.isSafeInteger` throw, and a standing ban on `BigInt` on the wire — four mechanisms defending an invariant Go gets from a type declaration. (2) **The raw body:** `net/http` parses nothing, so §2.3's failure 3 is *unrepresentable* rather than made structurally impossible by plugin encapsulation plus a CI grep. (3) **Dependency surface:** roughly six direct dependencies against ~15, with no Fastify-5 / Zod-4 / type-provider-5 / Kysely-0.28 / pg-boss-10 version matrix. (4) **Truth-flow:** `sqlc` derives types by having Postgres parse the query you actually ship, satisfying §4.2's own deciding criterion one level deeper than `kysely-codegen`, which derives *table* types and infers the result from a builder chain. Two further honest concessions: `pg-boss` installs a schema outside the committed `db/schema.sql` diff that §3.5 names as the mechanism making this design reviewable, and its default migrates at app boot — the thing §3.2 rejects by name; and this ADR's own migration tool, `dbmate`, is a Go binary chosen for a Go property.

**It is still rejected, for one reason.** This design deliberately pushed nearly all correctness into DDL — the exclusion constraint, the UNIQUE idempotency index, the settlement guard, the business-day CHECKs and trigger, `SKIP LOCKED`, the DSN timeouts. What remains in the application is a thin shell, and **the language of a thin shell is a low-stakes choice that should be settled by what else it touches.** What it touches is `apps/liff`, which is TypeScript and cannot be anything else — `liff.init()` resolves only in a browser — and which is roughly 60% of v1 by plan-weeks. The unit of work in this product is one person spending one afternoon on the sticky drawer *and* the endpoint behind it: `quote()`'s rate-boundary grouping and its Thai label string, the thirteen selection rules and their tests, every future `venue_config` change. One language crosses that seam zero times a week; two cross it on every feature, forever, at a headcount of one to three. **Go's advantages are all *within* the backend; the cost is paid *across* the seam, weekly.** At ~30 bookings a week nothing Go is good at has a workload to bind to, and everything the seam costs binds every week.

**Note what is not being claimed.** Throughput, memory footprint, container size and cold start are **not** criteria at this scale, and their appearance in a runtime argument is a reliable sign the runtime is being chosen for a different project. Nor is there sunk cost to defend: §9.2 gates the repo import on Plan 01 being approved and built, and it is neither. No code exists. This is the cheapest moment this decision will ever have, and the answer is still no — which is the useful part of the result.

**This decision flips if any of these becomes true. Each is checkable in under a day:**

| # | Condition | Why it flips |
|---|---|---|
| **a** | The person writing the backend is **Go-fluent and TypeScript-shallow**. D71 leaves the team blank — ask before Plan 03. | "One language" stops meaning Node and starts meaning the language the team actually has. |
| **b** | The team makes quotes **server-authoritative on every tap** — the client renders only server-returned `lines`, with no local `quote()`. | This deletes the deciding argument outright and Go wins on the merits. Price: a ~25–35 ms Singapore round trip on the app's best interaction, and a grid that degrades on venue wifi. Decide it explicitly rather than defaulting past it; `quoteToken` is already half a step down this road. |
| **c** | The backend acquires a **dedicated owner**. | A split along a real skill boundary is a different problem from a split across one person's afternoon. |

**The hatch that stays open, deliberately:** §4.1 already requires the contingent MQTT bridge — and any future SSE fan-out — to be a separately deployed, advisory-lock-guarded singleton. That deployable may be written in Go on its own merits without touching the booking API. Keeping the hatch open costs nothing, and it is the correct place for Go in this system if it ever earns one.

### 6.3 Three numbers worth reading twice

1. **At ten venues, PSP fees (~฿10,100) are more than twice the entire infrastructure bill (~฿4,957 — the §6.2 subtotal; an earlier draft said ฿4,660 here and ฿4,719 in the table, and the table was the one doing arithmetic).** That makes *"does the venue actually want prepayment, or is pay-at-counter fine?"* the **largest COGS decision in the product**, not a scope question — and it is why `PaymentProvider` plus D19's `booking.payment_method` must exist before either answer is known.
2. **One Official Account vs one per venue is ฿1,200 vs ฿12,000/month at ten venues.** A day-one schema decision (`venue_id` on `line_message`), not a later refactor.
3. **The cloud bill is noise against a salary.** At ten venues the entire infrastructure spend is roughly 4% of one Bangkok mid-level backend salary. The expensive resource is engineer-hours, and every exotic component spends them **monthly, forever** — which is the actual argument for this stack, not the ฿1,156.

### 6.4 What was deliberately not bought, and what it would have cost

Redis (~฿400/mo plus a stateful system to back up and patch) · a managed MQTT broker (฿0–700 and unnecessary until D37 clears) · Clerk / Auth0 (~฿850 plus a vendor on the critical path of a venue's Friday night) · Datadog (~฿500/host) · a transactional email vendor · a second staging **database** (a Neon branch is free — the staging *service* is not, and is now a line item in §6.1) · Turborepo remote caching · a materialised-view refresher.

## 7. Migration path

**If IoT ships (Plan 10, contingent on the clamp meter and D37).** Nothing structural changes, which is the point. Add an `apps/iot-bridge` deployable — **not** a subscriber inside the API — holding one `mqtt` client against a **managed** broker, wrapped in `pg_try_advisory_lock` so exactly one process holds the broker session regardless of how many run. Two new tables: `iot_device` and `light_session` (with `ends_at = booking.ends_at` and **no** `duration_min` column, per W7/D34). The 5-minute pre-off warning and the auto-off are `pg-boss` `sendAfter` jobs — **the same mechanism already built for the T−30 reminder.** The booking API changes by exactly one endpoint (`POST /light-sessions`, which checks that this `line_user_id` holds a confirmed booking for that court in that window before publishing). W7's inverted-QR model — a static pole QR encoding only `venue_id + court_id`, scanned inside an authenticated LIFF session — needs no new infrastructure at all. The relay **fails open** on a device-side TTL (W11), so a missed server timer is a lights-stay-on annoyance the hardware resolves, never a safety event. **Delta: one deployable, one free-tier vendor, two tables, two job handlers. Nothing decided today is orphaned if it never happens.**

**If the live scoreboard ships (v2, gated on D69's gang audit).** Add `GET /api/matches/:id/events` as **SSE** on the existing process, fanned out with Postgres `LISTEN/NOTIFY` on the **direct** database endpoint (the pooler breaks `LISTEN` — §3.2), with the listener advisory-lock-guarded or moved to its own deployable before a second instance exists. `EventSource` reconnects natively, which matters because the webview backgrounds constantly. Schema: `match` → `match_side` → `match_participant`, an append-only `rally` table and an append-only `exp_ledger` with `UPDATE`/`DELETE` revoked at the role level (D38/D45); no stored totals — `exp_total`, `win_rate_pct` and `current_streak` are views (D45/D46). **The binding constraint is not technical: it is the push budget.** The mockup promises a push every 15 s, which is ~208 pushes per 52-minute match against ฿40–80 of margin. D76's cap — **one push per set, never per point** — is an architecture decision made by arithmetic. Redis pub/sub or a realtime vendor becomes worth discussing somewhere past ~500 concurrent viewers per venue, which is a different product.

**At 50 venues (~6,500 bookings/month, ~300 courts).** **Nothing about the architecture changes, and that is the entire dividend.** Concretely: 3–4 app instances (already stateless, already `SKIP LOCKED`); `pg-boss` to its own Background Worker (a one-env-var flip); Neon to a larger compute with the owner-dashboard aggregates pointed at a read replica; **RLS on** via the `withTenant()` wrapper that already exists for this reason; per-venue rate limits on the availability endpoint; `pg-boss` to its own database if the queue becomes a noisy neighbour. Do **not** partition `booking` — 6,500/month is 78,000 rows a year and Postgres does not notice until tens of millions. Do **not** shard by venue — `venue_id` is on every table from migration 1, so tenancy is a `WHERE` clause. The one query that would genuinely strain the design is a cross-venue *"find me any free court near Ari at 19:00"* search, and the rule for that is: **materialise the search index, never materialise the inventory.**

**What actually breaks at 50 venues is not the servers.** It is 50 acquirer KYC processes and 50 sets of sealed merchant credentials (which is why `venue_payment_account` exists from migration 1) — **and that one does not wait for venue 50: at 2–6 weeks of KYC per venue, each needing that venue's company registration, and with the open question of whether our acquirer's merchant agreement even permits a platform to hold their keys (§3.4, §5), the onboarding pipeline is the binding constraint from roughly venue 3** — a LINE bill that needs per-venue cost attribution, PDPA data-subject requests from real people (a `DELETE /me` that cascades correctly), and a second engineer on call — who costs more per month than the entire infrastructure bill at **every** scale discussed in this document. **Plan for the operations, not the load.**

**If the business model flips to B2C-first.** `booking_item.kind = 'platform_fee'` already exists as a row (D67) and checkout already renders the `฿0 — ฟรีช่วงเปิดตัว` line, so turning on a take rate is a `rate_rule`-shaped data change plus a PSP split-settlement conversation. No schema migration.

## 8. Consequences

### 8.1 Good

- **Double-booking is impossible at the database level**, across all three insert paths, enforced by one line that no application refactor can bypass — and guarded by a 20-concurrent-request test plus a committed `schema.sql` that turns any weakening into a red diff in review.
- **Hold expiry needs no working job.** If every background worker is down for a week, nothing double-books and no peak inventory leaks.
- **The missed webhook is a designed-for case, not a hope** — the poller is primary, one CI test proves the system works with the webhook route disabled, and one narrowly-scoped daily digest — the only signal in the design that fires on an *absence*, and therefore the only one that must never page (§3.4) — watches for the event that never came.
- **The raw-body LINE bug is structurally impossible**, not policed by review discipline.
- **One origin, one deploy artifact, one language, one database, one bill.** No CORS layer, no service discovery, no cross-repo PR dance, and a LIFF endpoint URL that never changes.
- **Idle cost is ฿1,156/month and per-venue fixed cost falls as venues are added** — 17–33% of a venue's subscription at ten venues, against **39–77% at one** (§6.2 states the range, not a midpoint).
- **Plan 01's four surviving artifacts survive intact**, including its 19 state-machine tests, and its `api.ts` seam is the only file that changes when the backend arrives.
- **Nothing in the architecture is orphaned by the three biggest open questions.** If the venue says pay-at-counter, if slip verification is impossible, if IoT is cancelled — the schema, the host, the framework and the job system are unchanged.

### 8.2 Bad — stated plainly

- **One instance at pilot is a single point of failure, and every deploy is a 20–40 second outage.** The v1 mitigation is a written no-deploy window (17:00–22:00 ICT) enforced by nobody and obeyed by everybody, plus the owner console's "print today's bookings" so the venue can trade on paper for two hours. The engineered fix costs ~฿240/month and is deferred to the first paying venue. This is the most visible thing being traded away.
- **Two vendors means two status pages.** A database compute restart mid-peak is invisible until bookings start failing. Mitigated by pooled-endpoint retries and a `/healthz` that actually touches the database — but it is the real cost of not colocating app and data, paid to get branch-based restore drills and a swappable host.
- **The slot grid can be up to 20 seconds stale**, so two players can both see 19:00 on Court 3 as free and one receives a 409. At six courts and 130 bookings/month this happens perhaps twice a month. It is correct behaviour and a UI job — a clear Thai message plus an automatic refresh — and it is now `SLOT_TAKEN` in a closed error union so Plan 07 cannot forget it.
- **Plain-SQL migrations and generated types mean no CRUD scaffolding.** Month one is slower than Prisma. Expect ~20 extra minutes per schema change and a `schema.sql` diff in every PR.
- **Kysely is a weaker CV line than Prisma in Bangkok.** You will occasionally lose a candidate who wanted Prisma; you will gain one who can read an `EXPLAIN` plan. Put it in the job ad so nobody's time is wasted.
- **Types cannot enforce tenancy.** `TenantCtx` plus a lint rule catches the common case; until RLS is on at venue #2, the guarantee is convention plus one code path, which is a genuine downgrade from the rest of this design's standards. **The exception is `venue_payment_account`, which is behind RLS or its own role from `0001` (§3.3)** — deferring is a bet on blast radius, and that table's blast radius is ten venues' refund-capable merchant credentials.
- **No auto-generated OpenAPI, no generated client.** With one consumer written by the same people, that is documentation nobody reads. It becomes a real gap the day a venue's POS wants to integrate — at which point `zod-to-openapi` over schemas that already exist is about two days.
- **`pg-boss` shares the booking database.** At this volume that is a rounding error; at 50 venues it becomes a reason to give jobs their own database — not their own technology.
- **Kysely is pre-1.0 (0.28) and carries the entire data-access layer.** Accepted — its surface is small and `sql``` is the escape hatch that works regardless — but it is the one dependency in this design that semver does not protect, and it should be named here rather than discovered during an upgrade. Pin it exactly, like Tailwind in Plan 01.
- **No Redis means rate limiting is per-instance** and therefore up to 2× looser than configured once there are two instances. Accepted: the abuse surface is a LINE-authenticated human booking a badminton court. **Correction to an earlier draft of this line, which claimed the exclusion constraint "prevents the only attack that costs money": it does not.** The constraint prevents *double-booking*; it is perfectly happy to let one authenticated user hold all six courts across the whole Friday peak, fifteen minutes at a time, forever. Denial-of-inventory is the attack that costs the venue money, and it is stopped by the **`max_active_holds` per `(app_user_id, venue_id)` check inside the hold transaction** (§3.3), not by rate limiting and not by the constraint. Per-instance rate limiting remains up to 2× looser than configured at two instances, and that is the accepted part.
- **Flex templates as compiled TypeScript mean every copy change is a deploy.** Correct at 17 templates and two people; wrong at 50 or when a marketing person wants to edit them.
- **Sequential booking references (`WC-YYMM-NNNN`, per venue per month) leak booking volume** to anyone who books twice. Recorded so it is a decision, not an oversight. **How the number is produced is also a decision, and it is in `0001`** — a `booking_ref_counter(venue_id, yymm, next_val)` row upserted with `INSERT … ON CONFLICT (venue_id, yymm) DO UPDATE SET next_val = booking_ref_counter.next_val + 1 RETURNING next_val`, called inside the booking transaction. `SELECT max()+1` races under two concurrent inserts and hands two customers the same reference; the upsert takes a row lock for the rest of the transaction, which serialises only bookings for the *same venue in the same month* and is exactly the scope that needs it. A real per-venue-month `SEQUENCE` was rejected: it needs DDL at runtime and leaves an object per venue per month behind forever.
- **One timezone assumption is baked into the seed and the reminder helper.** Every Thai venue is UTC+7 with no DST, and `venue.timezone` is already a row, so a venue outside ICT is a data change plus one helper — but the assumption exists.
- **Push delivery is best-effort, and for a customer who never adds the OA it is nothing at all.** `pushMessage` requires friendship (§3.4), so the confirmation, the T−30 reminder and the apology are all optimisations layered over the LIFF confirmation screen and the `.ics`. The add-friend step will not convert everyone, and the honest consequence is that **some paying customers get their receipt only on screen, and the venue reaches them by phone.** That is a designed fallback rather than a fixable defect, and it is why `contact_phone` is required at checkout.
- **The refund path may be a person, not an API.** If the chosen acquirer has no synchronous PromptPay refund (§5's second quote question), every `paid_orphan` and every D16 cancellation refund becomes a queue item, a form asking a customer for their bank account, and a 5-day SLA someone has to own. Longer holds (15 min) and a charge expiry ≤ the hold make it rare; nothing makes it impossible, and at pilot volume "rare" still means a handful a quarter with real money attached.

### 8.3 The single biggest risk

**One Postgres instance holds both the correctness model and the single point of failure, and its correctness lives in DDL that no future hire will have written before.**

The realistic failure is not an outage. It is **dilution**. A hire in month fourteen, chasing a slow grid on a Friday, proposes a `court_slot` cache table. Someone adds an ORM "for productivity" and the constraint becomes invisible in the codebase. Someone writes the walk-in endpoint in a hurry and puts the stale-hold reap *outside* the transaction, and it works — until a duel-accept and a counter walk-in land in the same 40 ms and one silently wins. **That bug does not throw.** It shows up as a venue owner shouting at two groups standing on Court 3 at 19:00 on a Friday, which is the moment this company loses its pilot.

Six mitigations, all cheap, all **in the repo rather than in someone's head**:

1. The **20-concurrent-confirm test** — exactly one 201, nineteen 409s — in its own committing harness (§3.5), beside the **different-`play_date` test** that proves the constraint still keys on the day and the **midnight-hole test** that proves the business-day rule holds.
2. A plain-language comment block above the constraint in `0001_core.sql` naming the three insert paths and stating that application guards will not survive all three.
3. `db/README.md` — **four rules on one page**: money is satang `bigint` · availability is generated by `availability(venue_id, play_date)`, never a table · rates are rows, never constants · migrations are expand/contract. Plus the two-dimensional-constraint alternative recorded as a **considered rejection**, so it is not re-invented in month six.
4. `db/schema.sql` committed and diffed in CI on every migration.
5. The CI greps, each aimed at a named defect class.
6. `db/RESTORE.md` with **the last drill date at the top**.

And the one rule a new hire will break, which deserves its own line: **no network I/O — no LINE push, no PSP call — ever happens inside an open transaction.** An `await` inside a transaction holds a GiST index lock and blocks every booking on that court until it times out. Three timeouts are set **in the connection string** — `idle_in_transaction_session_timeout=5s`, `lock_timeout=3s`, `statement_timeout=10s` — not in a migration (§3.2: `ALTER DATABASE … SET` reaches only *new* sessions, and `:"DBNAME"` is a psql variable dbmate cannot execute). `lock_timeout` is the one that turns this failure from a hang into an error: a second transaction waiting on the GiST check against an uncommitted conflicting row **blocks**, it does not raise `23P01`, so without a bound the whole court queues behind one slow insert path. The transaction helper is the **only** way to open a transaction.

### 9.3 The first three files — in this order, and nothing else until they are done

These three encode the three decisions that are expensive to reverse. Write them before a single route.

**1 · `db/migrations/0001_core.sql`** — the whole product's correctness, ~200 lines of hand-written SQL:

```sql
-- migrate:up
CREATE EXTENSION IF NOT EXISTS btree_gist;

-- NO `ALTER DATABASE ... SET` here. `:"DBNAME"` is a psql variable and dbmate
-- runs SQL through a Go driver, so that line is a syntax error and migration 1
-- fails; and ALTER DATABASE ... SET only reaches NEW sessions anyway. The three
-- timeouts live in the DSN (§3.2):
--   ?options=-c%20idle_in_transaction_session_timeout%3D5s
--            -c%20lock_timeout%3D3s -c%20statement_timeout%3D10s

-- venue · venue_config · court · rate_rule · app_user · staff_user · staff_session
-- booking_group · booking · booking_ref_counter · payment_intent
-- venue_payment_account · webhook_event · line_message · audit_log
-- Every table: venue_id NOT NULL. Money: *_satang bigint. Status: text + CHECK,
-- never a Postgres ENUM (ALTER TYPE cannot remove a value; text+CHECK reverses
-- in two lines — the register's three-day rule says take the option that
-- deletes the most schema).
-- venue_config also carries: open_min, close_min, slot_min, max_active_holds.

-- Business-day rule (§3.2). play_date is the venue's BUSINESS day, so a
-- 23:00-01:00 slot is (D,1380,1500) and the 00:00-01:00 slot after it is
-- (D,1440,1500) — never (D+1,0,60), which the constraint could not see.
ALTER TABLE booking
  ADD CONSTRAINT booking_slot_sane CHECK (
    start_min >= 0 AND end_min > start_min
    AND end_min <= start_min + 1440   -- no booking spans more than a day
    AND end_min <= 2160               -- and never more than one midnight
  ),
  -- The predicate column. Maintained with status, tied to it by a CHECK that —
  -- unlike EXCLUDE — supports NOT VALID, so adding 'no_show' later never
  -- rebuilds the GiST index under ACCESS EXCLUSIVE. See §3.3.
  ADD CONSTRAINT booking_occupies_matches_status CHECK (
    occupies_slot = (status IN ('held','confirmed','checked_in','completed'))
  );

-- The per-venue half of the business-day rule needs a join, which a CHECK
-- cannot do. BEFORE INSERT OR UPDATE: reject start_min < venue_config.open_min
-- or end_min > open_min + 1440. Backstop for wc_canonical_slot(), which every
-- insert path calls to turn (wall_date, start_min, duration) into
-- (play_date, start_min, end_min).
CREATE TRIGGER booking_business_day BEFORE INSERT OR UPDATE ON booking
  FOR EACH ROW EXECUTE FUNCTION wc_assert_business_day();

-- THE line. Three code paths insert bookings: the LIFF client, duel-accept, and
-- the counter walk-in. Application guards will not survive all three. Do not
-- weaken this; see db/README.md, the 20-concurrent-confirm test, and the
-- different-play_date test.
-- play_date WITH = IS LOAD-BEARING: without it, the second booking ever made
-- for this court-hour on ANY other date is rejected as SLOT_TAKEN and the
-- product is dead on day 2. btree_gist is why `date WITH =` works here.
ALTER TABLE booking ADD CONSTRAINT booking_no_overlap
  EXCLUDE USING gist (
    venue_id WITH =,
    court_id WITH =,
    play_date WITH =,
    int4range(start_min, end_min, '[)') WITH &&
  ) WHERE (occupies_slot);

-- WC-YYMM-NNNN, per venue per month. SELECT max()+1 races and hands two
-- customers the same reference; this takes a row lock for the rest of the
-- booking transaction, scoped to one venue-month.
CREATE TABLE booking_ref_counter (
  venue_id uuid NOT NULL REFERENCES venue(id),
  yymm     char(4) NOT NULL,
  next_val integer NOT NULL,
  PRIMARY KEY (venue_id, yymm)
);
-- Called inside the booking transaction:
--   INSERT INTO booking_ref_counter (venue_id, yymm, next_val)
--   VALUES ($1, $2, 1)
--   ON CONFLICT (venue_id, yymm)
--   DO UPDATE SET next_val = booking_ref_counter.next_val + 1
--   RETURNING next_val;   -- -> format('WC-%s-%s', yymm, lpad(v::text,4,'0'))

-- availability(venue_id, play_date) — a FUNCTION, not a view: a view has no row
-- source for FREE slots and takes no parameters (§3.3). generate_series over
-- venue_config's opening hours CROSS JOIN court, LEFT JOIN live bookings,
-- LEFT JOIN LATERAL the winning rate_rule.
```

**2 · `apps/api/src/db/index.ts`** — the two type parsers, the Kysely instance, and the only transaction helper:

```ts
import pg from 'pg';

// int8 (satang) arrives as a STRING by default: total_satang + 100 becomes
// "44000100". 2^53 satang is ~฿90 trillion, so number is safe — with a guard.
pg.types.setTypeParser(20, (v) => {
  const n = Number(v);
  if (!Number.isSafeInteger(n)) throw new Error(`int8 out of safe range: ${v}`);
  return n;
});

// date (OID 1082) otherwise becomes a JS Date at the PROCESS's local midnight.
// Under TZ=Asia/Bangkok, '2026-09-11' -> 2026-09-10T17:00:00Z, and
// .toISOString().slice(0,10) then mis-dates the entire booking inventory by a
// day. Booking inventory is a LOCAL CALENDAR DAY. Keep it a string.
pg.types.setTypeParser(1082, (s) => s);

// MANDATORY, not optional. `pg` emits 'error' on an IDLE client when the server
// cuts the connection — which Neon does on every maintenance restart. An
// unhandled 'error' event on an EventEmitter is an uncaught exception, so the
// single always-on instance dies at an hour Neon picks, with nothing in Sentry.
export const pool = new pg.Pool({ connectionString: env.DATABASE_URL });
pool.on('error', (err) => log.error({ err }, 'idle pg client error'));

// The only way to open a transaction. Rule: no network I/O inside one — ever.
// An await on a LINE push or a PSP call holds a GiST lock and blocks every
// booking on that court until idle_in_transaction_session_timeout fires.
export const tx = async <T>(fn: (trx: Trx) => Promise<T>): Promise<T> => { /* … */ };
```

### 9.5 The console settings that silently break the product, before anyone writes a line of LINE code

Every item here is a **checkbox in a console**, none of them produce a stack trace, and each has cost someone a day.

**1 · Create the LINE Login channel and the Messaging API channel under the SAME LINE provider.** If they sit under different providers, the LIFF ID token's `sub` is a different `userId` than `pushMessage` accepts, every booking confirmation 400s, it looks like an auth bug, and it is **not fixable after the channels are created.** Put this in the runbook and in a comment in the LIFF auth module.

**2 · LINE OA Manager — four settings that break the bot in ways that look like code faults.** Response mode must be **Bot**, not Chat (Chat mode suppresses webhook-driven replies while the console cheerfully shows the account as working); **"Use webhook" must be ON** (it is off by default on a fresh OA, and a webhook that is configured, verified and simply never called is the most confusing state in the platform); and **auto-reply messages and the greeting message must be OFF**, or every user gets a canned reply next to — or instead of — the one the product sent, and the duplicate is billed.

**3 · LIFF app settings.** Scopes must include **`openid`** — without it `liff.getIDToken()` returns **`null`** and login "just doesn't work" with nothing in any log (§3.4) — plus `profile`. Turn the **add-friend option** on, which is half of the friendship design in §3.4. The endpoint URL is the same origin that serves the SPA (§3.5), which is what keeps `BrowserRouter` viable.

**4 · Cloudflare, before the webhook URL is pasted into either console.** Add an explicit **WAF / Bot Fight Mode skip rule for `/webhooks/*`** and set SSL/TLS to **Full (strict)**, not Flexible. Cloudflare's managed rules and Bot Fight Mode **challenge LINE's webhook POSTs** — LINE cannot solve a challenge, it retries, it fails, and it **auto-disables the webhook endpoint**, at which point pushes still work and inbound events silently stop. Flexible TLS re-encrypts to plaintext at the origin and is a signature-verification and privacy problem for the same path. Then, when you press **Verify** in the console: it POSTs a body with an **empty `events` array**, so the Zod schema must accept `events: []` (§3.4) or verification fails against a webhook that is in fact working perfectly.

**5 · Do all four of the above *twice*.** Staging needs its **own LINE Login channel, its own Messaging API channel and its own LIFF app**, created under the **same provider** as production (rule 1 applies there and is equally unfixable there), pointed at the **paid** staging service from §6.1 — a free-tier service spins down, LINE's POST hits a cold start, and the endpoint is auto-disabled exactly as in rule 4. This is the console day §6.1 budgets. Doing it while you are already in these screens is an hour; doing it three weeks later, from memory, is the day.
